# SmartBank AI — Fraud & Risk Intelligence Platform

SmartBank AI is a learning-oriented portfolio project for transaction fraud detection and customer risk analysis. It combines synthetic banking data, classical ML, anomaly detection, sequence learning, SHAP explanations, SQL persistence, a FastAPI service, and a Streamlit dashboard. The generated records are synthetic and are not representative of real banking customers.

## Features

- Reproducible synthetic dataset with 10,000 customers and 100,000 transactions by default.
- Behavioral fraud labels, customer churn labels and customer risk scores.
- Leakage-aware preprocessing, feature engineering, train/test split and training-only resampling.
- Logistic Regression, Random Forest and XGBoost model comparison using held-out metrics.
- Isolation Forest and a TensorFlow reconstruction-error autoencoder.
- Customer-grouped chronological LSTM sequences.
- Customer risk score regression and churn probability classification.
- Local SHAP explanations for fraud predictions.
- SQLite/SQLAlchemy persistence with PostgreSQL URL support.
- FastAPI endpoints with interactive Swagger documentation and a Streamlit dashboard.
- Pytest coverage, Dockerfile and Docker Compose configuration.

## Architecture

```text
Synthetic CSVs → preprocessing → supervised models / anomaly models / LSTM
                                  ↓
                           saved model bundles
                                  ↓
Streamlit dashboard → FastAPI → SQLAlchemy → SQLite (PostgreSQL URL supported)
                         └── SHAP explanations
```

## Requirements

Python 3.11 is the recommended local version. TensorFlow and XGBoost are substantial dependencies; installation and model training can take several minutes. Create a virtual environment and install dependencies:

```bash
python -m venv .venv
# Windows PowerShell: .venv\Scripts\Activate.ps1
# macOS/Linux: source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

Copy `.env.example` to `.env` when configuring a non-default database or API URL. No credentials or secrets are required for the local SQLite configuration.

## Run the project

Run commands from the project root. First generate data. If you generated it before the customer-risk fields were added, regenerate it so the customer CSV contains `risk_score` and `risk_category`.

```bash
python -m src.data.generate
python -m src.preprocessing.prepare
```

### Train models

```bash
python -m src.models.train_fraud
python -m src.models.train_customer
python -m src.models.train_anomaly
python -m src.models.train_lstm
```

`train_anomaly` trains both Isolation Forest and the autoencoder. To skip the TensorFlow autoencoder, pass `--skip-autoencoder`. The LSTM groups transactions by customer and time, creates ten-event sequences by default, and keeps customers disjoint between its training and validation subsets. Sequence-window predictions are more useful when real customer history is supplied; the single-transaction API route documents its repeated-window approximation.

The fraud model is selected by test-set PR-AUC. Its test set retains the natural class distribution, while the training portion is resampled. Reports include accuracy, precision, recall, F1, ROC-AUC, PR-AUC and confusion matrices; the reports are generated by real training runs and are not checked into this source tree. Customer risk is a regression score in [0, 100], while churn returns a probability. The autoencoder cutoff is learned from the 99th percentile of validation reconstruction errors. Isolation Forest also uses a validation-derived score cutoff.

Model artifacts are written into `models/`:

| Artifact | Purpose |
| --- | --- |
| `fraud_model.pkl` | Selected fraud classifier, fitted preprocessor and feature metadata |
| `fraud_model_metrics.csv/json` | Held-out comparison results |
| `risk_model.pkl`, `churn_model.pkl` | Customer risk and churn bundles |
| `anomaly_model.pkl` | Isolation Forest and fitted transformations/cutoff |
| `anomaly_model_metrics.json` | Validation score threshold and anomaly rate |
| `autoencoder.keras` | Normal-transaction reconstruction model |
| `lstm_model.keras` | Transaction-sequence classifier |
| `lstm_metrics.json` | LSTM validation metrics and sequence split size |
| `customer_model_metrics.json` | Risk regression/churn classification metrics and churn feature importance |

Artifacts use Python pickle/joblib formats and should only be loaded from trusted sources.

### Start the API and dashboard

```bash
uvicorn src.api.main:app --reload
```

The API is available at `http://localhost:8000`; Swagger UI is at `http://localhost:8000/docs`. In a second terminal:

```bash
streamlit run streamlit_app.py
```

The dashboard is available at `http://localhost:8501`. Generate the CSV files first for the overview, customer and transaction pages. The fraud analysis page calls the API and requires the fraud artifact. Customer and transaction API tables can be loaded with `python -m database.seed` after data generation.

### API reference

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/` | Service information |
| GET | `/health` | Health and fraud artifact availability |
| POST | `/predict/fraud` | Fraud probability and optional `?explain=true` SHAP reasons |
| POST | `/predict/risk` | Customer score from 0 to 100 and category |
| POST | `/predict/churn` | Customer churn probability |
| POST | `/predict/anomaly` | Isolation Forest anomaly score |
| POST | `/predict/lstm` | LSTM sequence probability |
| GET | `/transactions` | Recent persisted transactions |
| GET | `/customers` | Customer profiles |
| GET | `/alerts` | Persisted fraud alerts; optional `?level=HIGH` |
| GET | `/model-performance` | Generated fraud-model metrics |

Prediction inputs are validated with Pydantic. A missing model returns HTTP 503 with the relevant training command. Predictions are recorded in SQL; positive fraud predictions also create alerts.

### Database

SQLite is used by default at `data/smartbank.db`. SQLAlchemy configuration is in `database/database.py`; tables are declared in `database/models.py`. To switch to PostgreSQL, install a PostgreSQL driver such as `psycopg[binary]` and set `DATABASE_URL` to a SQLAlchemy URL such as `postgresql+psycopg://user:password@host:5432/smartbank`.

## Testing

```bash
pytest -q
```

Tests cover data generation, feature engineering, API health/docs/input validation and a SQLAlchemy database round trip. Model training tests are intentionally not part of the fast test suite because TensorFlow training is resource intensive.

## Reference local training run

The following is the actual seeded run produced while building this workspace (100,000 synthetic transactions, fraud rate 2.14%, random seed 42). It is a reproducibility example, not a claim of production performance.

| Fraud model | Accuracy | Precision | Recall | F1 | ROC-AUC | PR-AUC |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Logistic Regression | 0.7435 | 0.0477 | 0.5794 | 0.0882 | 0.7193 | 0.0957 |
| Random Forest | 0.9787 | 1.0000 | 0.0023 | 0.0047 | 0.6813 | 0.0770 |
| XGBoost | 0.8719 | 0.0587 | 0.3318 | 0.0998 | 0.6690 | 0.0708 |

The low precision and recall trade-offs show why accuracy alone is misleading for this imbalanced task. The selected logistic model uses the default 0.5 threshold; operating thresholds should be tuned against explicit investigation capacity and fraud-loss costs before any real use. Actual per-run metrics are written to `models/` and are excluded from version control.

The same seeded run produced customer-risk regression MAE 5.87 (R² 0.63), churn ROC-AUC 0.635, and LSTM validation ROC-AUC 0.50 / PR-AUC 0.0218. The LSTM result is at the validation baseline and is not useful yet; it is included as an evaluated learning implementation, with improved sequence signal and temporal validation left as future work. Isolation Forest and autoencoder thresholds are validation cutoffs, not measures of fraud-classifier accuracy.

## Docker

Generate data and train at least the fraud model first so the mounted API can serve predictions. Then:

```bash
docker compose up --build
```

The API runs on port 8000 and the dashboard on port 8501. Generated data, model files and the SQLite database are bind-mounted from the project directory. TensorFlow makes the image large; the image is intended for local learning and portfolio review.

## Limitations and future improvements

The labels, entities and performance are synthetic. The current LSTM inference route accepts one transaction and pads its sequence window by repeating the current row; a production design should fetch prior transactions for that customer. The API currently uses a single local-process model load per request and is not production-hardened. Future work could add real privacy-reviewed datasets, temporal backtesting, threshold tuning by business costs, migrations, authentication, model monitoring, drift checks, CI and deployment automation.
